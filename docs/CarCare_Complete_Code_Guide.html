1. Application Architecture & Master Navigation Flow

CarCare is built using the industry-standard 3-Tier Architecture. This cleanly separates user interface, business logic, and database operations:

Layer Package Location Core Responsibility
1. Presentation Layer PresentationLayer.* JFrame and JDialog GUI screens designed in NetBeans Matisse, FlatLaf styling, user input capture, table rendering, button event handling.
2. Business Layer BusinessLayer.* Domain Entities (Customer, Vehicle, Service, Bill) and Business Logic Services (Login_BLL, Vehicle_BLL, Customer_BLL) containing input validations and business rules.
3. Data Access Layer DataAccessLayer.* Raw database interaction via JDBC (PreparedStatement, ResultSet), executing SQL queries against the MySQL carcare_db database.

System Launch Sequence

Here is the exact step-by-step process of how the application boots up when you run it:

  1. Entry Point: Execution starts in LoginForm.main() (Line 250).
  2. Look & Feel Setup: FlatLightLaf.setup() applies modern rounded cards, clean typography, and native OS anti-aliasing.
  3. Login Window Displays: LoginForm appears on screen, centered vertically and horizontally.
  4. Authentication Flow:
    • User types email and password, then clicks the "LOGIN" button (or presses Enter).
    • LoginForm.handleLogin() (Lines 39-63) extracts inputs and calls Login_BLL.login(email, password).
    • Login_BLL trims strings, verifies non-empty, and delegates to Login_DAO.validateLogin(email, password).
    • Login_DAO executes: SELECT * FROM users WHERE email = ? AND password = ?.
    • If true: this.dispose() destroys the login window and new VehicleManagement_Screen().setVisible(true) opens the master application window!
  5. Master Window Initialization: VehicleManagement_Screen constructor runs:
    • setupWindow(): Sets title, dimensions (1100×700), navy blue background.
    • setupTabs(): Instantiates all 6 sub-screens (Dashboard_Screen, CustomerManagement_Screen, ServiceQueue_Screen, Billing_Screen, Appointment_Screen, ServiceManagement_Screen), extracts their internal panels via getter methods, and inserts them into jTabbedPane1!
    • setupControls() & setupTable(): Configures vehicle search bar, action column renderer, and pagination.
    • loadVehicles(): Loads active cars into memory.
Evaluator Defense Tip: If your evaluator asks "Where does the application start and how does it navigate?", answer:
"The application begins in LoginForm.main(), which initializes FlatLaf modern UI. When credentials are validated by Login_BLL and Login_DAO, LoginForm closes itself and launches VehicleManagement_Screen. VehicleManagement_Screen is our master container window that embeds the main panels of all other screens into a JTabbedPane."

2. Database Schema, Relationships & Foreign Keys

The database is named carcare_db running on MySQL via XAMPP. After our system audit and cleanup, there are exactly 9 active, fully-connected tables. All unused tables (payments, service_record_items) and duplicate indexes were cleanly removed.

Table Name Rows Primary Key Outbound Foreign Keys Role in System
users 2 user_id None Stores administrator login credentials (email & password).
customers 6 customer_id None Master directory of vehicle owners (name, phone, email, address).
vehicles 7 vehicle_id customer_id → customers Registered vehicles with unique registration number, make, model, year, mileage.
mechanics 4 mechanic_id None Workshop technicians with specialization and availability status.
services 5 service_id None Workshop service catalog (e.g. Oil Change, Brake Inspection, Wheel Alignment).
appointments 3 appointment_id customer_id → customers
vehicle_id → vehicles
mechanic_id → mechanics		 Future bookings with date, time, status ('Pending', 'Confirmed', 'Completed').
service_records 2 record_id vehicle_id → vehicles
mechanic_id → mechanics		 Core work order table binding cars, assigned mechanics, date, service description.
service_queue 2 queue_id vehicle_id → vehicles
record_id → service_records		 Live FIFO workshop bay queue with queue position, start time, completion time.
bills 2 bill_id record_id → service_records (UNIQUE 1:1) Customer invoices with service total, parts, discount, grand total, status ('Paid', 'Unpaid').

Referential Integrity & Cascade Rules

  • Customer Deletion Cascade: vehicles.customer_id → customers.customer_id ON DELETE CASCADE. If a customer is deleted, all their registered vehicles and appointments are automatically removed by MySQL engine.
  • Vehicle Deletion Cascade: service_records.vehicle_id → vehicles.vehicle_id ON DELETE CASCADE and service_queue.vehicle_id ON DELETE CASCADE. Deleting a car cascades to queue items and work logs.
  • Mechanic Safety: service_records.mechanic_id → mechanics.mechanic_id ON DELETE SET NULL. If a mechanic profile is deleted, historical service records are preserved with mechanic_id = NULL rather than destroyed.
  • Billing 1:1 Unique Constraint: bills.record_id has a UNIQUE constraint, guaranteeing that each completed service job has at most ONE invoice.
Audit Note: Why were payments and service_record_items removed?
During the audit, we found that payments had 0 rows because the application updates bills.status = 'Paid' directly instead of writing separate payment ledger slips. Similarly, service_record_items had 0 rows because work orders store service names directly in service_records.description. Removing these 2 unused tables simplified the database and prevents evaluator penalties for dead schema.

Automatic Tab-Switch Data Refresh Listener

When the user clicks on any tab, an event listener detects the tab index change and immediately re-queries the database so the data is always 100% fresh! Look at lines 125-143 of VehicleManagement_Screen.java:

jTabbedPane1.addChangeListener(e -> {
    int idx = jTabbedPane1.getSelectedIndex();
    if (idx == 0 && dashboardScreen != null) {
        dashboardScreen.loadDashboardStats(); // Refresh metric counts & activity
    } else if (idx == 1) {
        loadVehicles(); // Refresh vehicles table
    } else if (idx == 2 && customerScreen != null) {
        customerScreen.loadCustomers(); // Refresh customers table
    } else if (idx == 3 && queueScreen != null) {
        queueScreen.loadQueueData(); // Refresh FIFO queue & active bay
    } else if (idx == 4 && billingScreen != null) {
        billingScreen.loadBills(); // Auto-create & fetch invoices
    } else if (idx == 5 && appointmentScreen != null) {
        appointmentScreen.loadAppointments(); // Refresh appointment calendar
    } else if (idx == 6 && serviceScreen != null) {
        serviceScreen.loadServices(); // Refresh catalog & vehicle combos
        serviceScreen.loadVehicles();
    }
});
Key Takeaway: Switching tabs is reactive and live. If you add a car in the Vehicles tab and switch to the Dashboard tab, the "Total Vehicles" metric immediately updates without needing to restart the application!

4. Data Access Layer (DAO) — Every Function & SQL Query

All database queries reside exclusively in the DataAccessLayer package. Every function uses parameterized PreparedStatement to prevent SQL Injection.

4.1 DB_Connection.java — Database Connection Factory

Purpose: Establishes a JDBC physical connection to MySQL.

public class DB_Connection {
    private static final String URL = "jdbc:mysql://localhost:3306/carcare_db";
    private static final String USER = "root";
    private static final String PASSWORD = "";

    public Connection getConnection() {
        try {
            return DriverManager.getConnection(URL, USER, PASSWORD);
        } catch (SQLException e) {
            System.out.println("Database connection failed!");
            e.printStackTrace();
            return null;
        }
    }
}

5. Business Logic Layer (BLL) & Domain Entities

The BusinessLayer package encapsulates domain entities (POJOs) and business validation services.

5.1 Business Services

1. Login_BLL.java

public class Login_BLL {
    private final Login_DAO loginDAO;

    public Login_BLL(Login_DAO loginDAO) {
        this.loginDAO = loginDAO;
    }

    public boolean login(String email, String password) {
        // Business Rule: Null or empty credentials are rejected before hitting DB
        if (email == null || email.trim().isEmpty()) return false;
        if (password == null || password.trim().isEmpty()) return false;
        return loginDAO.validateLogin(email.trim(), password);
    }
}

2. Vehicle_BLL.java

public class Vehicle_BLL {
    private Vehicle_DAO vehicleDAO = new Vehicle_DAO();

    public List<Vehicle> getAllVehicles() {
        return vehicleDAO.getAllVehicles();
    }

    public boolean addVehicle(Vehicle vehicle) {
        // Business Rules:
        if (vehicle == null) return false;
        if (vehicle.getRegistrationNo() == null || vehicle.getRegistrationNo().trim().isEmpty()) return false;
        if (vehicle.getVehicleYear() < 1900 || vehicle.getVehicleYear() > 2030) return false;
        if (vehicle.getMileage() < 0) return false;
        return vehicleDAO.addVehicle(vehicle);
    }

    public boolean deleteVehicle(String registrationNo) {
        if (registrationNo == null || registrationNo.trim().isEmpty()) return false;
        return vehicleDAO.deleteVehicle(registrationNo.trim());
    }
}

8. In-Depth Billing & Invoicing Mechanics

The Billing module (Billing_Screen.java) is one of the most sophisticated modules in CarCare. Here is exactly how it functions:

8.1 Automatic Invoice Generation

When the user clicks the Billing tab, Billing_DAO.getAllBills() executes. Before returning the list, it calls autoCreateBills() (Lines 58-75 in Billing_DAO.java):

INSERT INTO bills (record_id, bill_date, service_total, grand_total, status)
SELECT sr.record_id, CURDATE(), 5000, 5000, 'Unpaid'
FROM service_records sr
LEFT JOIN bills b ON sr.record_id = b.record_id
WHERE b.bill_id IS NULL AND sr.status = 'Completed'

What this SQL query does: It finds every service job in service_records that has status = 'Completed' but does not yet have a matching invoice in bills. It automatically creates an invoice for today's date with status = 'Unpaid'. Because of the UNIQUE KEY (record_id) constraint, duplicate bills are impossible!

8.2 The Invoice Detail Card

When an invoice row is clicked in jTable1, showBillDetails(Bill b) (Lines 492-519) populates the right-hand panel (jPanel3):

  • Header: Displays Invoice number (#INV-101), customer name, vehicle make/model, and license plate.
  • Itemized Breakdown:
    • Service package base cost (e.g. Rs. 5,000)
    • Extra Parts / Addons (if total > 5,000, calculated as total - 5000)
    • Diagnostics & Inspection (included, highlighted in green)
    • Workshop Labor Charges (included, highlighted in green)
  • Subtotal & Tax: Displays subtotal and tax.
  • Payment State: If status is 'Paid', the "Collect Payment" button is automatically disabled and labeled "Paid". If 'Unpaid', the button is enabled in blue.

8.3 The Dynamic Discount Engine

When the user changes the discount dropdown (jComboBox1), applyDiscount() (Lines 522-532) fires:

private void applyDiscount() {
    if (selectedBill == null) return;
    int idx = jComboBox1.getSelectedIndex();
    double discountPct = (idx == 1) ? 0.05 : (idx == 2) ? 0.10 : 0.0;
    double discountAmt = selectedBill.getTotal() * discountPct;
    double grandTotal = selectedBill.getTotal() - discountAmt;

    jLabel10.setText("-Rs. " + String.format("%.0f", discountAmt));
    jLabel13.setText("Grand Total: Rs. " + String.format("%.0f", grandTotal));
}
  • Index 0: "No Discount (0%)" → Grand Total = Full Total
  • Index 1: "Loyalty Discount (5%)" → 5% deducted
  • Index 2: "Corporate Fleet (10%)" → 10% deducted

8.4 Adding Extra Parts to Bill

When the "+ Add Extra Part" button (jButton1) is clicked, addExtraPart() prompts JOptionPane.showInputDialog("Enter Part Price (Rs):"). If the user enters 1500:

  1. It calculates newTotal = selectedBill.getTotal() + 1500.
  2. It calls billingDAO.updateBillTotal(selectedBill.getBillId(), newTotal).
  3. Executes: UPDATE bills SET grand_total = ? WHERE bill_id = ?.
  4. Reloads the bills list, and the itemized card automatically shows: "Extra Parts / Addons: Rs. 1,500"!

9. Evaluator Defense Q&A (Questions & Exact Answers)

Here are the exact questions your evaluator is guaranteed or likely to ask, along with the precise, professional answers you should give:

Q1: What architecture does this application follow and why did you choose it?
Your Answer: "CarCare follows the 3-Tier Architecture: Presentation Layer, Business Layer, and Data Access Layer. I chose this to decouple UI components from database logic. The UI handles user input and styling, the Business Layer enforces validation rules, and the Data Access Layer executes SQL queries. This makes the system maintainable, testable, and prevents database code from leaking into GUI forms."
Q2: How is the database connected and how do you prevent SQL injection?
Your Answer: "The database is connected via JDBC using DB_Connection.getConnection(), which connects to MySQL on localhost:3306. To completely prevent SQL injection, every single query in our DAOs uses java.sql.PreparedStatement with '?' placeholders. User input is never concatenated directly into SQL strings."
Q3: How does the application transition from Login to the main Dashboard?
Your Answer: "When the user clicks Login, LoginForm.handleLogin() validates the credentials via Login_BLL and Login_DAO. Upon successful authentication, LoginForm calls this.dispose() to free memory and instantiates new VehicleManagement_Screen().setVisible(true). VehicleManagement_Screen is our master window that hosts all the workshop tabs."
Q4: How do the tabs work in your system? Are they separate windows?
Your Answer: "No, they are not separate windows. VehicleManagement_Screen contains a JTabbedPane. In setupTabs(), it instantiates each screen class (Dashboard_Screen, CustomerManagement_Screen, ServiceQueue_Screen, Billing_Screen, etc.) and extracts their main content panels using getter methods like getDashboardPanel() or getBillingPanel(). It embeds these panels into the tab bar. When the user switches tabs, a ChangeListener automatically refreshes the data for that tab from MySQL."
Q5: How does the FIFO service queue work?
Your Answer: "The service queue implements a First-In, First-Out (FIFO) structure. When a car is added to the queue via addToQueue(), it is assigned the next queue_position (MAX + 1). ServiceQueue_DAO.getWaitingQueue() returns a Queue<ServiceTicket> backed by a Java LinkedList. When the workshop manager clicks 'Call Next Vehicle', callNextVehicle() polls the head of the queue, updates its status to 'In Service' in Bay 1, and decrements all other waiting queue positions by 1."
Q6: What happens when you register a vehicle? Explain the database flow.
Your Answer: "When the user clicks 'Register & Save' in AddVehicle_SCREEN, it performs a dual-entity transaction: first, it saves the customer via Customer_DAO.addCustomer() using RETURN_GENERATED_KEYS to obtain the auto-increment customer_id. Then, it creates the Vehicle object using that customer_id and saves it via Vehicle_DAO.addVehicle(). This maintains strict referential integrity."
Q7: How does billing work when a service is finished?
Your Answer: "When a service is marked as completed in the queue, its status becomes 'Completed'. When the manager opens the Billing tab, Billing_DAO.autoCreateBills() executes an INSERT INTO bills ... SELECT query that automatically generates an unpaid invoice for any completed service record that doesn't yet have an invoice. The manager can then add extra parts, apply discounts, collect payment, and print the receipt."
Q8: How did you fix the login screen centering issue on full screen?
Your Answer: "In the NetBeans Matisse design section of LoginForm.form and initComponents(), the top margin was previously hardcoded as a fixed 75px gap while the bottom was flexible. I updated the top gap to be a flexible container gap with pref=75, max=Short.MAX_VALUE. Now both top and bottom margins expand equally like springs, keeping the login card perfectly centered on any resolution."
Q9: Why are there 9 tables in your database instead of 11?
Your Answer: "During our code and database audit, we verified that the payments table and service_record_items table had 0 rows and were never referenced in our Java source code. Our application records payment status directly on the bills table and stores service descriptions in service_records. To maintain a clean, normalized, and production-ready schema, we dropped those two redundant tables."
Q10: What third-party libraries did you use?
Your Answer: "We used two libraries: FlatLaf 3.7.2 for modern, rounded, clean UI styling, and MySQL Connector/J 26.7.0 for high-performance JDBC connectivity with MySQL."
